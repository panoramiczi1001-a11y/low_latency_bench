# C++ 容器与堆分配：跨架构实测

**一句话结论：`reserve` 在 n=100 时把 vector 构造的中位耗时砍掉约一半、尾部砍掉一到两倍；但这个收益随规模衰减，到 n=10000 时尾部优势完全消失。**

两套硬件上跑同一份代码：

| | 平台 A | 平台 B |
|---|---|---|
| 架构 | x86-64 | ARM64 (AArch64) |
| CPU | Intel Core Ultra X9 388H | Snapdragon 8cx Gen 3 |
| 环境 | Linux 虚拟机，2 vCPU | 容器 |
| `clock_getres` | 1 ns | 1 ns |
| **实测单次读数开销** | **约 22 ns** | **约 250 ns** |

---

## 要回答的问题

1. 栈数组、`malloc`、`std::vector`、`reserve + push_back` 四种形态差在哪？
2. `-O2` 能优化掉什么、优化不掉什么？
3. `reserve` 的收益在**中位数**和**尾延迟**上是否一致？
4. 同一份代码换架构，结论会不会变？

第 3 条是重点。低延迟工程里人人都在说「要 reserve」，但很少有人给出「它到底改善均值还是尾部」的实测。

---

## 怎么跑

```bash
make all                       # 编译 8 个二进制（4 实现 × O0/O2）
make run                       # 计时，默认 n=100 rounds=20000 rep=100
make run N=10000 ROUNDS=500 REP=10
make record N=100 ROUNDS=5000 REP=100    # 结果写入 results/results.txt
```

测试驱动默认用 `test_p99.cpp`（输出分位数与计时开销）；`make TEST_SRC=test.cpp` 可切回只报 `best/avg` 的原始版本。

> 参数不是随便定的：`rep` 决定测量窗口大小。ARM 上读一次时钟要 250 ns，`rep=20` 时计时开销会占到 25% 以上，结果不可信。

---

## 方法

四个被测实现统一暴露 `int f(int n)`，由 `test_p99.cpp` 跨编译单元调用，**避免被测代码被内联进计时循环**：

| 文件 | 实现 |
|---|---|
| `3ptr.cpp` | 栈数组 `int a[100]`，先写再求和 |
| `3malloc.cpp` | `malloc` 后两趟循环，结尾 `free` |
| `3vector.cpp` | `push_back` 循环 + 迭代器求和 |
| `3vecres.cpp` | `reserve(n)` 后 `push_back` |

计时循环：

```cpp
for (int r = 0; r < rounds; r++) {
    t0 = now_sec();
    for (int k = 0; k < rep; k++) sink += f(n);
    t1 = now_sec();
    samples.push_back((t1 - t0) / rep * 1e9);
}
```

三个设计决定：**内层重复 `rep` 次再摊回单次**（把测量窗口放大到微秒级）；**保留全部样本报分位数**（最小值回答不了「会不会偶尔卡一下」）；**同时测量计时器自身开销**（它决定结果的可信上限）。

## 结果

### n=100（纳秒）

| 实现 | x86 O0 p50 | x86 O0 p99 | x86 O2 p50 | x86 O2 p99 | ARM O0 p50 | ARM O0 p99 | ARM O2 p50 | ARM O2 p99 |
|---|---|---|---|---|---|---|---|---|
| 栈数组 | 352.0 | 831.3 | **49.2** | **123.6** | 450.1 | 1041.3 | 88.9 | 129.3 |
| malloc | 293.0 | 731.4 | 55.3 | 88.5 | 453.8 | 1320.9 | 83.4 | 182.4 |
| reserve | 743.1 | 1865.1 | 80.6 | 237.0 | 1106.4 | 1830.6 | **91.7** | **135.7** |
| vector | 1279.4 | 3708.7 | **160.0** | **353.2** | 2278.8 | 7181.2 | 172.3 | 374.9 |

### n=10000（仅 vector 两组有效，见「测量踩坑」）

| 实现 | ARM O0 p50 | ARM O0 p99 | ARM O2 p50 | ARM O2 p99 |
|---|---|---|---|---|
| reserve | 93910 | 231820 | 7630 | 12930 |
| vector | 99780 | 316860 | **9220** | **11260** |

---

## 结论

### 1. 跨平台一致：`reserve` 在 n=100 时约快 2 倍

O2 下 vector 对 reserve 的中位耗时：x86 160.0 → 80.6（1.99×），ARM 172.3 → 91.7（1.88×）。

原因明确：不 reserve 时容量从 1 翻到 128 要 **7 次重新分配**，每次都是 `operator new` + `memcpy` + `operator delete`，n=100 时这笔账分摊到 100 次 push 上占比很高。

同时栈数组、malloc、reserve 三者在 O2 下基本持平（x86 49 / 55 / 81，ARM 89 / 83 / 92）。**单次堆分配本身不是瓶颈，反复扩容才是。**

### 2. 尾部收益在 ARM 上远大于中位数

O2 下 p99 的改善比：x86 是 353.2 / 237.0 = **1.49×**，ARM 是 374.9 / 135.7 = **2.76×**。

同一段代码、同一个机制，ARM 的尾部收益接近 x86 的两倍。推测是容器环境的调度抖动更大，不 reserve 时的扩容尖峰更容易和外部抖动叠加——**这是推测，未做受控实验分离变量。**

### 3. 收益随规模衰减，n=10000 时尾部优势消失

n=10000 时：p50 是 9220 → 7630（1.21×），但 **p99 是 11260（不 reserve）对 12930（reserve）**——不 reserve 的一组尾部反而更稳。

一万次 push 里扩容只发生 14 次，固定成本被摊薄，尾部由系统噪声主导。**`reserve` 解决的是「小规模、高频构造」的尖峰；规模一大，瓶颈换人。**

### 4. `-O2` 的收益取决于被优化的是什么

| 实现 | x86 O0→O2 (p50) | ARM O0→O2 (p50) |
|---|---|---|
| 栈数组 | 7.2× | 5.1× |
| vector | 8.0× | **13.2×** |

`-O2` 对 **vector** 的收益在 ARM 上明显更大（13.2× 对 8.0×）：O0 下每次 `push_back` 都是完整函数调用加迭代器检查，弱核心上这部分占比更高，一旦内联收益更显著。但对**栈数组**，ARM 的收益反而比 x86 小。

**「弱核心更依赖优化」只对了一半**——取决于被优化的是哪类代码。

### 5. 编译器不会因 `reserve` 消除容量检查

反汇编确认：即使 `reserve(n)` 且循环恰好 n 次，`push_back` 内的 `cmp size, capacity` 与扩容分支依然完整保留。GCC 不会做「循环次数等于预分配容量」这种推理。

要得到完全无分支的写入路径，只能改写成 `resize` + 下标赋值，或加入编译器无法反驳的约束（循环内 `if (size == capacity) __builtin_abort();`）。

## 测量踩过的坑

这一节是整份实验最该保留的部分——**好几个结论差点因为下面这些陷阱变成错的**。

**数组版在 n>100 时越界。** `3ptr.cpp` / `3malloc.cpp` 固定 `int a[100]`，跑 n=10000 时段错误或 `malloc(): corrupted top size`。所以 n=10000 只有 vector 两组数据有效，表格里留空不是没跑，是跑不了。

**分辨率与开销是两件事。** `clock_getres` 报 1 ns，但 ARM 上实测单次读数耗时约 250 ns。分辨率是「最小能表示多少」，开销是「读一次要多久」，**真正起作用的是后者**——它决定单次计时的误差量级是 ±250 ns 而不是 ±1 ns。

早期版本给单次 `f` 计时，结果全是 100 的整数倍（500、200、1100…），一度以为分辨率是 100 ns。真实原因更可能是读数开销远大于被测值。改用重复放大法后，O2 组之间的差异才显现。

**最小值不是可靠的比较依据。** `max` 比 `p99` 大几十倍（微秒到十几微秒），那是调度和中断。`best` 也会被一次幸运采样带偏（x86 上 malloc 的 O0：best 142.8 而 p50 355.4，差一倍多）。**跨组比较用 p50，讨论最坏情况用 p99，`best`/`max` 只用于判断是否存在系统性干扰。**

**计时开销的占比必须交代。** `rep=100` 时每轮读两次时钟约 500 ns，摊到每次 `f` 是 5 ns，相对 O2 结果（80–172 ns）占 3%–6%，可接受。若用 `rep=20`，占比升到 25% 以上。

---

## 局限

1. 两套环境都是虚拟化/容器，**不是裸机**，绝对值不代表硬件能力。
2. n=10000 只有 vector 两组有效。
3. 未测 `resize + 下标赋值` 这条替代路径，结论 5 的建议缺少数据支撑。
4. 结论 2 的解释是推测，未做受控实验。
5. 单线程测量，未涉及多线程下的伪共享。

---

## 对低延迟工程的可操作结论

1. 小规模、高频构造的容器必须 `reserve`，收益约 2 倍，尾部收益更大。
2. 不要指望编译器替你消除扩容检查；要无分支热路径得改写入方式。
3. 热路径上的容器操作应放在同一编译单元，或开启 LTO。
4. 规模变大时优化重点会转移，别对着已经不成问题的地方做优化。
5. 纳秒级测量必须先量测量工具本身：读一次时钟多久、分辨率多少、重复多少次才够。
