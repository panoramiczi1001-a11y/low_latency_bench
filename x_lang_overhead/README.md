# 附：语言运行时开销 —— C++ vs CPython

**起因**：同一道题（平衡二叉树判定）在 LeetCode / NeetCode 上分别用 C++ 和 Python 提交，
平台读数约 **3 ms vs 43 ms**（14×）。这个数字能不能当结论用？这组实验是为了回答它。

## 一、假设

调用密集的负载（递归、逐节点分支），两者差距应该远大于常见的「10 倍」口径，
因为 CPython 每层调用都要建帧、查类型、维护引用计数，而这些开销随调用次数线性叠加。

## 二、方法

**同一棵隐式完全二叉树**（下标 `2i+1` / `2i+2` 寻址），同一个递归「判平衡」函数，逐行对应：

- 不建真实的节点和指针——建树开销会混进结果，而这里要量的只是「函数调用 + 分支」。
- 两个子节点**总是都被访问**，只是先后顺序由 `a[i] & 1` 交换。工作量与「从左到右」完全一致，
  但编译器无法把结果折成常量。
- 两版用**同一串 LCG**（固定种子 12345）生成数据，访问的是同一棵树。
- 计时用 `common/timer.h`，绑核 `taskset -c 0`，报 p50 / p90 / p99。

**防优化三招**（第一版在这里栽过，见第五节）：`noinline`、每次重复前 `a[0] ^= 1`、
结果写进 `volatile sink`。

## 三、结果

环境：Intel Core Ultra X9 388H **虚拟机 2 vCPU** / g++ 11.4 `-O2 -std=c++20` / CPython 3.10.12。
原始输出：`results/x86-intel-ultra9-388h/x_lang_overhead.txt`。

| 节点数 | C++ p50 | C++ 每节点 | CPython p50 | CPython 每节点 | 倍数（p50） |
|---|---|---|---|---|---|
| 32,767 | 74.2 µs | 2.26 ns | 8.34 ms | 254.5 ns | **112×** |
| 131,071 | 307.0 µs | 2.34 ns | 32.92 ms | 251.2 ns | **107×** |
| 524,287 | 1.24 ms | 2.36 ns | 139.05 ms | 262.7 ns | **112×** |

**每节点成本在两个语言里都是常数**（2.3 ns vs 250 ns），所以差距随规模线性放大，规模本身不影响倍数。

## 四、结论

1. **同一份算法、同一棵树、同一台机器，C++ 比 CPython 快约 110 倍。**
   到「每节点多少纳秒」这一层，两个数字都很稳定，可以当结论用。
2. **平台那个 14× 是被固定开销压扁的。** 13 万个节点在 C++ 里真实计算只要 **0.3 ms**，
   而平台报 3 ms——多出来的部分是输入解析、进程启动和判题系统的计时粒度。
   也就是说：**平台读数里的 C++ 那 3 ms 基本是地板，不是计算时间**；把地板减掉，倍数才回到百倍量级。
3. **尾部差异同样值得看**：C++ 这边 p99/p50 ≈ 2–3×（沙箱 2 vCPU 的调度噪声），
   Python 这边反而更「齐」（p90/p50 ≈ 1.05）——因为它慢得足够久，噪声被淹没。
   **「稳定」不等于「可控」，慢的分布窄并不代表尾延迟好。**

## 五、坑：第一版报出 29 ns / 13 万节点

第一次跑，C++ p50 = 29 ns，折算 0.0002 ns/节点。原因是**整段递归被 GCC 常量折叠**：
函数只依赖 `n` 和下标结构，不依赖数据内容，结果对每次重复都相同，于是被提到循环外。

**怎么一眼看出测错了**：那次的 p50 是 29 ns，而同一份输出里计时器自身开销是 20–35 ns——
**「一次判 13 万个节点」比「读一次时钟」还便宜，这在物理上不可能**。拿测量开销当尺子，
是所有性能实验最便宜的自检方式。`noinline` 挡不住它：不变的是**参数**，不是调用。
必须让参数或数据在每次重复之间真的变（这就是 `a[0] ^= 1` 的作用）。

这类实验的第一课不是「测量」，是**先证明 CPU 真的在干活**。修法是让结果依赖数据
（子树访问顺序随 `a[i]` 交换），并在每次重复前破坏循环不变量。

## 六、五组对比：C++ / Cython / numba / PyPy / CPython

同一个算法、同一棵树、同一串 LCG 数据，**全部绑到 CPU 0**，131,071 节点，取 p50。
Windows 原始输出：`results/x86-intel-ultra9-388h/x_lang_overhead_win.txt`。

| 组 | ns/节点 | 相对 CPython | 比上一行快 |
|---|---|---|---|
| 纯 CPython 3.14 | **195.2** | 1× | — |
| PyPy 3.12（JIT，代码不动） | **12.6** | 15.5× | 15.5× |
| numba（`@njit`） | 9.4（未绑核读数，绑核后进程异常退出，待补） | 21× | 1.3× |
| Cython（`cdef` + 指针） | **5.25** | 37× | 1.8× |
| 纯血 C++（MSVC /O2） | **2.57** | **76×** | 2.0× |

**结论不是排名，是「每一层抽象值多少倍」**：只换解释器（CPython→PyPy，代码一行不改）就买回 15 倍；
把热点函数编译掉（numba / Cython）到 37 倍；写成 C++ 到 76 倍。
**七成收益在「离开解释器」这一步，剩下三成在「离开 Python 语义」。**
所以标准切法是「研究层 Python + 交易路径 C++」，而不是把整个项目重写一遍。

### 这组数最值钱的地方：口径错了会得出反向结论

| 组 | 未绑核 | 已绑核 | 变化 |
|---|---|---|---|
| C++ | 7.97 | **2.57** | 快 **3.1×** |
| PyPy | 28.7 | **12.6** | 快 **2.3×** |
| CPython | 276.3 | **195.2** | 快 1.4× |
| Cython | 5.00 | 5.25 | 噪声内 |

**未绑核那一轮，C++ 跑不过 Cython（7.97 vs 5.00），会直接得出「C++ 不如 Cython」的错误结论。**
绑核之后同一个二进制是 2.57，稳稳快一倍。Core Ultra 的 P 核/E 核迁移足以让结论反转。

### 顺带排除的两个假设

- **`noinline`**：曾以为它让 C++ 慢了 3 倍，实测只差 2.2 vs 2.4 ns（8%），是噪声。
  写一个实验时「为了公平」禁掉编译器优化，本身就不公平——内联是 C++ 的能力之一。
- **`/GL` 全程序优化**：2.59 vs 2.57，无差别。

### 复现步骤

Linux：`bash four_way.sh [nodes] [repeats]`；Windows：`four_way.bat 131071 100`。
缺 Cython / PyPy 的那组自动跳过。**每组跑三次以上**，单次读数只能当「有没有跑通」。

## 六点五、Windows 怎么跑

`taskset` 和 `clock_getres` 是 Linux 的东西。Windows 上：

- **绑核**：C++ 版在 `main()` 里调 `SetProcessAffinityMask`；Python 三组用 `pin.py`（ctypes 直调，
  不用装 psutil）。**注意 ctypes 必须声明 `GetCurrentProcess` 的 `restype`**，
  否则 64 位伪句柄 `-1` 被截成 32 位，`SetProcessAffinityMask` 静默失败（这个坑踩过）。
- **计时**：`timer.h` 已加 `_WIN32` 分支，报 100 ns 的 QPC 分度（Linux 上是 `clock_getres` 的 1 ns）。
  Windows 上计时器自身开销读到 0 ns，是因为 QPC 分度粗于两次读取的间隔，不代表没有开销。
- **编译器**：详见下面的 MSVC 坑。

| 要跑哪组 | 装什么 | 大小 / 说明 |
|---|---|---|
| CPython | 已有 | — |
| 纯血 C++ | **w64devkit**（解压即用，含 g++/make/gdb）或 MSYS2 | ~80 MB，无需管理员 |
| PyPy | pypy.org 的 Windows 64 位 zip，解压后把目录加进 PATH | ~30 MB |
| Cython | `pip install cython setuptools` **加一个 C 编译器**：MSVC Build Tools（3–5 GB），或 w64devkit + `%USERPROFILE%\pydistutils.cfg` 里写 `[build]` / `compiler=mingw32` | 后者省空间，配置略绕 |

跑：`four_way.bat 131071 100`

**MSVC 的坑（踩过）**：源码是 UTF-8 带中文注释，而 MSVC 默认按系统代码页（936/GBK）解码。
GBK 双字节字符的第二个字节可能是 `0x5C`（反斜杠），行接续又发生在去注释之前，
于是下一行被吞进注释，报出来的却是一串 `'return'`、`'public'` 的语法错误。
**解法：加 `/utf-8`。** `cl /nologo /O2 /std:c++20 /EHsc /utf-8 /I..\common bench_cpp.cpp /Fe:bench_cpp.exe`

**cl.exe 不在全局 PATH**：先 `call "<VS>\VC\Auxiliary\Build\vcvars64.bat"` 初始化环境。

## 七、限制

- 沙箱是 **虚拟机 2 vCPU**，不是裸机；绝对值不可直接和别的机器比，倍数可以。
- 只测了**一种负载形状**（调用密集 / 分支密集）。对**向量化负载**（numpy 能整体改写的任务），
  两者差距会小得多——这正是「为什么撮合引擎必须 C++，而回测可以 Python」的分界线。
- **numba 那组绑核后异常退出**（JIT 首次调用处静默退出，无报错、无输出），未绑核时正常（9.4 ns）。
  表里那一格用的是未绑核读数，标注为待补。**这是已知缺口，不要当结论引用。**
- **四组的解释器版本不完全一致**（CPython 3.14.6 / PyPy 3.12.15），因为 PyPy 的最新版落后一个语言版本；
  语言版本差异对这类纯算术递归影响很小，但不是零。
- `abs()` 在 Python 里是函数调用，C++ 里是内联比较——这条差异本身就在测「调用开销」里，
  属于**要测的现象**，不算污染。
